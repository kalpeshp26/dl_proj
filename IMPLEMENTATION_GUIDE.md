## 1. Project Overview

**DeepRetail** is a single-camera autonomous checkout and retail intelligence system. It uses a laptop webcam pointed at a physical shelf and basket to:

- Detect and track physical products in real time
- Identify which product is which using deep learning
- Detect when products are picked up or returned
- Flag unregistered items, unknown products, misplaced products, and low stock
- Maintain a live cart, inventory, and billing dashboard

**The entire codebase is written and tested.** All 7 stages, both phases, 96 automated tests passing. The only thing the user must do is collect product images, annotate a subset, train the models, and calibrate the camera zones.

## 3. System Architecture

```
WEBCAM (fixed, calibrated once)
        │
        ▼
┌─────────────────────────┐
│  STAGE 1 — Detection     │   YOLOv8n
│  outputs: product / hand │   NEVER outputs product identity
│  bounding boxes only     │
└────────────┬────────────┘
             │
             ▼
┌─────────────────────────┐
│  STAGE 2 — Tracking      │   Custom IoU tracker
│  assigns persistent      │   Hungarian algorithm
│  track_id per product    │   (scipy.optimize)
└────────────┬────────────┘
             │
        ┌────┴────┐
        ▼         ▼
┌──────────────┐  ┌─────────────────┐
│  STAGE 3     │  │  STAGE 4        │
│  Classifier  │  │  Zone Logic     │
│  MobileNetV3 │  │  shelf / basket │
│  + embedding │  │  slot ROIs      │
└──────┬───────┘  └────────┬────────┘
       │                   │
       ▼                   │
┌──────────────┐           │
│  STAGE 3b    │           │
│  Open-Set    │           │
│  cosine dist │           │
│  → UNKNOWN?  │           │
└──────┬───────┘           │
       └──────────┬────────┘
                  ▼
┌─────────────────────────────┐
│  STAGE 5 — State Machine     │   Pure Python, rule-based
│  SHELF → HELD → BASKET       │   No LSTM / Transformer
│  = pick event                │
│  BASKET → HELD → SHELF       │
│  = return event              │
│  HELD timeout → ANOMALY      │
└─────────────┬───────────────┘
              │
              ▼
┌─────────────────────────────┐
│  STAGE 6 — FastAPI Backend   │
│  SQLite DB, cart, inventory  │
│  analytics, alerts, WS push  │
└─────────────┬───────────────┘
              │
              ▼
┌─────────────────────────────┐
│  STAGE 7 — Streamlit UI      │
│  live feed, cart, alerts     │
│  inventory, recommendations  │
└─────────────────────────────┘
```

**Key design rules (enforced in code):**
- YOLO only localizes — never identifies product type
- No LSTM or Transformer for action recognition — state machine is rule-based
- One camera only
- PyTorch throughout — no TensorFlow
- Every stage logs to JSONL independently

## 7. Step-by-Step User Workflow

### 7.1 — Physical Setup

Before touching the computer:
- Place your products on a shelf or elevated surface
- Place a tray/basket/box below or beside the shelf
- Position the webcam so it sees **both** the shelf and the basket in one frame
- Fix the camera — **do not move it after calibration**
- Ensure good, consistent lighting

### 7.2 — Edit Your Product List

Open `src/config.py` and change `PRODUCT_CLASSES` to your actual products:

```python
PRODUCT_CLASSES = [
    "coke_500ml",
    "pepsi_500ml",
    "lays_classic",
    "oreo",
    "kitkat",
    # add or remove as needed — 5 to 8 products
]
```

Rules:
- Use lowercase, no spaces (use underscores)
- These names must match the folder names you create in the next step
- These names will appear in the dashboard and cart

### 7.3 — Collect Product Images

Run this command for each product. The webcam opens. Hold the product in front of the camera. Press **SPACE** to save a frame. Rotate, tilt, move it around for variety. Aim for **150–200 images per product**.

```bash
venv\Scripts\activate

python src/data_tools/capture_images.py --class coke_500ml
python src/data_tools/capture_images.py --class pepsi_500ml
python src/data_tools/capture_images.py --class lays_classic
python src/data_tools/capture_images.py --class oreo
python src/data_tools/capture_images.py --class kitkat

# Also collect background/negative images
python src/data_tools/capture_images.py --class background --limit 50
```

**Controls during capture:**
- `SPACE` — save the current frame
- `q` — quit / move to next class

Images are saved to `data/raw_images/<class_name>/`

**Tips for good images:**
- Include images with your hand partially blocking the product
- Vary the background (table, shelf, held in air)
- Include images at different distances
- Try different lighting conditions

### 7.4 — Copy Images to Classifier Dataset

```bash
# Windows CMD
xcopy /E /I data\raw_images data\classifier_dataset
```

This makes the classifier dataset folder match the raw images.

### 7.5 — Annotate Images for YOLO

**Download LabelImg** (free, portable .exe):
👉 https://github.com/HumanSignal/labelImg/releases

Steps in LabelImg:
1. Launch LabelImg
2. Click **Open Dir** → open `data/raw_images/coke_500ml/`
3. Click **Change Save Dir** → point to `data/yolo_dataset/labels/`
4. On the left panel, click the format button until it shows **YOLO**
5. Press `W` to draw a box → drag around the product → type `product` → confirm
6. If a hand is visible in the frame, draw another box → label it `hand`
7. Press `D` to go to next image, `Ctrl+S` to save

**You only need to annotate ~200–300 images total.** Not all of them — pick a varied subset from across all your product classes.

After annotating, copy the image files:
```bash
# Copy annotated image files to yolo_dataset/images/
xcopy /E data\raw_images\* data\yolo_dataset\images\ /Y
```

Your folder should look like:
```
data/yolo_dataset/
    images/
        coke_0001.jpg
        coke_0002.jpg
        ...
    labels/
        coke_0001.txt    ← auto-saved by LabelImg
        coke_0002.txt
        ...
```

### 7.6 — Train YOLO

```bash
# Generate data.yaml and split into train/val
python src/data_tools/create_yolo_yaml.py

# Train YOLOv8n (50 epochs, ~30-60 min on CPU)
python src/detection/train_yolo.py
```

When finished, `models/yolo_best.pt` will appear.

Optional — verify it works:
```bash
python src/detection/yolo_infer.py --source 0
```
You should see the webcam with green boxes around products and blue boxes around hands. Press `q` to quit.

### 7.7 — Train the Product Classifier

```bash
python src/classification/train_classifier.py
```

This runs in two phases automatically:
- Phase A (~5 epochs): trains only the final classification layer
- Phase B (~15 epochs): fine-tunes the entire network

Takes ~20–40 minutes on CPU. When done, `models/classifier_best.pt` appears and a confusion matrix is printed.

Check `logs/classifier_eval.json` for validation accuracy — aim for ≥85%.

### 7.8 — Build Open-Set Centroids

```bash
python src/classification/openset.py
```

This processes all your training images to compute the "average embedding" for each product class. Takes 2–5 minutes. Output: `models/class_centroids.npy`.

After this, the system can say "I don't recognize this object" for things it was never trained on.

### 7.9 — Calibrate Camera Zones

Point your camera at your physical setup exactly as it will be during the demo. Run:

```bash
python calibrate.py
```

Follow the interactive prompts:
1. It captures a frame from your webcam and saves it as `calibration_snapshot.jpg`
2. **Shelf ROI**: drag a rectangle around the entire shelf area → press ENTER
3. **Basket ROI**: drag a rectangle around the basket/tray → press ENTER
4. **Shelf slots**: drag a rectangle around each product's position on the shelf → press ENTER after each one, type the low-stock threshold when asked (default: 3)
5. Press ESC to stop adding slots

A preview image `calibration_preview.jpg` is saved showing all your defined zones.

> **Important:** After calibrating, do not move the camera. If you move it, run `calibrate.py` again.

## 9. Demo Guide — All 6 Scenarios

Run all 6 in one session without restarting anything between them.

---

### Scenario 1 — Normal Purchase

**What to do:**
Pick a product from the shelf. Hold it briefly. Place it in the basket.

**What the system does:**
- YOLO detects the product bounding box
- Tracker assigns a track ID
- Classifier identifies the product name
- State machine transitions: SHELF → HELD → BASKET
- `pick` event fires
- Dashboard cart updates with product name and price
- Inventory count decrements
- Event appears in AI activity log

**Pass criteria:** Product name correct in cart, total updates, event logged.

---

### Scenario 2 — Return

**What to do:**
Pick the product from the basket. Place it back on the shelf.

**What the system does:**
- State machine transitions: BASKET → HELD → SHELF
- `return` event fires
- Cart removes the item
- Inventory count restores
- Event appears in log

**Pass criteria:** Cart empties, inventory restores.

---

### Scenario 3 — Unregistered Item / Anomaly

**What to do:**
Pick a product from the shelf. Hold it in your hand for more than 10 seconds. Don't put it in the basket or return it to the shelf. Walk away or hide it.

**What the system does:**
- State machine sees the track in HELD state for longer than `ANOMALY_TIMEOUT_SEC` (10 seconds)
- `anomaly` event fires
- Red `ANOMALY` alert appears on dashboard: "Unregistered item detected. Staff verification required."
- Alert logged to `logs/alerts.jsonl`

**Pass criteria:** Alert appears within ~10–12 seconds of picking up the product.

---

### Scenario 4 — Unknown Product

**What to do:**
Hold an object that was **never in your training set** in front of the camera — e.g. your phone, a pen, a water bottle (if not trained), a stapler.

**What the system does:**
- Classifier extracts embedding
- Cosine distance to all class centroids exceeds `OPENSET_DIST_THRESH`
- Returns `UNKNOWN` instead of guessing a product name
- Dashboard shows `UNKNOWN PRODUCT` — nothing added to cart
- Logged with `is_unknown: true`

**Pass criteria:** No product name shown, no cart update, UNKNOWN visible on feed.

---

### Scenario 5 — Misplaced Product

**What to do:**
Take a Pepsi bottle (or any wrong product) and place it in the Coke slot on the shelf. Leave it there for several seconds.

**What the system does:**
- Shelf monitor checks detected product vs expected product for that slot
- Counter increments each frame — alert does NOT fire immediately (flicker suppression)
- After `MISPLACED_CONSECUTIVE_FRAMES` (10 frames ≈ ~0.7 seconds), alert fires
- `MISPLACED_PRODUCT` alert on dashboard: "Expected coke_500ml, detected pepsi_500ml in slot_0"

**Pass criteria:** Alert fires with correct expected vs detected names. Does NOT fire if you just briefly wave the wrong product over the slot.

---

### Scenario 6 — Low Stock

**What to do:**
Keep picking products from the same slot one by one (putting them in the basket each time) until the stock count drops to 3 or below.

**What the system does:**
- Each `pick` event decrements the DB stock count for that product
- When `stock <= low_stock_threshold` (default: 3), a `LOW_STOCK` alert fires
- Dashboard shows: "Low stock: coke_500ml (2 remaining, threshold=3)"
- Alert clears automatically if you return items and stock goes back above threshold

**Pass criteria:** Alert fires exactly at the threshold crossing. Clears when restocked.

## 11. Configuration Reference

All tunable values live in `src/config.py`. Change them here only — they propagate everywhere automatically.

| Constant | Default | What it controls |
|---|---|---|
| `PRODUCT_CLASSES` | 8 products | Your physical product names — edit this first |
| `YOLO_CONF_THRESH` | 0.40 | Minimum detection confidence — lower = more detections, more noise |
| `YOLO_EPOCHS` | 50 | YOLO training epochs |
| `OPENSET_DIST_THRESH` | 0.48 | Open-set rejection sensitivity — lower = stricter (more UNKNOWNs) |
| `TRACK_IOU_THRESH` | 0.30 | Minimum IoU to re-associate a detection to a track |
| `TRACK_MAX_AGE` | 15 | Frames before an unseen track is deleted |
| `ANOMALY_TIMEOUT_SEC` | 10.0 | Seconds held without resolution before anomaly fires |
| `MISPLACED_CONSECUTIVE_FRAMES` | 10 | Frames of wrong product before misplaced alert |
| `LOW_STOCK_DEFAULT_THRESHOLD` | 3 | Default minimum stock level |
| `CAMERA_INDEX` | 0 | Webcam index — change to 1 if laptop has two cameras |
| `TARGET_FPS` | 15 | Pipeline frame rate cap |
| `API_PORT` | 8000 | FastAPI server port |

### Tuning tips

- If too many `UNKNOWN` on real products → **increase** `OPENSET_DIST_THRESH` (e.g. 0.45)
- If unrecognized objects are being classified as real products → **decrease** `OPENSET_DIST_THRESH` (e.g. 0.25)
- If anomaly fires too fast → **increase** `ANOMALY_TIMEOUT_SEC`
- If misplaced alerts fire from brief movements → **increase** `MISPLACED_CONSECUTIVE_FRAMES`
- If products aren't being detected → **decrease** `YOLO_CONF_THRESH`

## 12. Troubleshooting

**"YOLO weights not found"**
→ Run `python src/detection/train_yolo.py`

**"Classifier weights not found"**
→ Run `python src/classification/train_classifier.py`

**"No centroids file"**
→ Run `python src/classification/openset.py` after classifier training

**"Cannot open camera"**
→ Try changing `CAMERA_INDEX` to `1` in `config.py`
→ Verify: `python -c "import cv2; cap=cv2.VideoCapture(0); print(cap.isOpened())"`

**Every product shows as UNKNOWN**
→ Increase `OPENSET_DIST_THRESH` in `config.py` (try 0.45 or 0.50)
→ Check that `models/class_centroids.npy` exists

**Classifier accuracy < 85%**
→ Collect more images, especially with varied lighting and partial occlusion
→ Make sure class folder names exactly match `PRODUCT_CLASSES` in config

**Dashboard shows no camera feed**
→ Run pipeline in a separate terminal: `python src/pipeline/run_pipeline.py`
→ Ensure backend is running before the dashboard

**"SQLite locked" error**
→ Restart the backend: `uvicorn src.backend.main:app --host 127.0.0.1 --port 8000`

**Anomaly fires during normal picks (false positives)**
→ Increase `ANOMALY_TIMEOUT_SEC` in `config.py`

**Misplaced alert fires when briefly moving products**
→ Increase `MISPLACED_CONSECUTIVE_FRAMES` in `config.py`

**Wrong camera index**
→ Check `CAMERA_INDEX` in `config.py` — 0 is usually the built-in webcam, 1 is external

## 13. Viva / Technical Defence Notes

These are the key points an examiner will ask about. Know these cold.

---

**Q: Why does YOLO only detect "product" and "hand"?**

A: YOLO is a localization tool in this system. Its job is only to answer "is there a product here, and where?" — not "which product is it?" Product identity comes from the MobileNetV3 classifier in Stage 3, which receives a cropped image of the detected product. This strict separation means the detection model is simple, fast, and retrainable with very few images.

---

**Q: Why not just use YOLO to classify products too?**

A: YOLO would require hundreds of images per product class to distinguish between them reliably, and retraining would mean retraining the entire detector. Separating detection (Stage 1) from classification (Stage 3) means we can add new products by training only the lightweight MobileNetV3 classifier, without touching YOLO at all.

---

**Q: How does the tracker work?**

A: It uses the Hungarian algorithm (`scipy.optimize.linear_sum_assignment`) to find the minimum-cost assignment between current-frame detections and existing tracks. Cost is `1 - IoU` (Intersection over Union). If two boxes overlap well, they're matched. Each track gets a persistent integer ID that follows the object across frames even through occlusion, because the track survives up to 15 unseen frames before being dropped.

---

**Q: How does open-set rejection work?**

A: After classifier training, we pass all training images through the model and record the 1024-dimensional embedding vector for each one. We compute the mean embedding (centroid) per class. At inference time, we extract the embedding for a new product crop and compute the cosine distance to the nearest class centroid. If this distance exceeds a threshold (0.48 by default), we return `UNKNOWN` — the object is too far from anything we've seen. This is more robust than using softmax confidence alone, because softmax always produces a distribution that sums to 1 and will confidently misclassify unseen objects.

---

**Q: Why rule-based state machine instead of an action recognition model?**

A: An action recognition model (LSTM, Transformer) would require labeled video sequences of pick and return actions — expensive to collect and hard to debug. The rule-based state machine is transparent: if a product centroid leaves the shelf zone and enters the basket zone, it's a pick. This is explainable, deterministic, and can be reasoned about without any training data. The spec document explicitly requires this approach.

---

**Q: What happens if the demo webcam fails?**

A: The pipeline has a video file fallback mode. Before the demo, record a test session. If the camera fails, run:
`python src/pipeline/run_pipeline.py --source recording.mp4`
The same pipeline processes the video file identically to a live feed.

---

**Q: How is inventory kept consistent if picks and returns happen fast?**

A: All stock mutations in `db.py` use a Python threading lock plus SQLite transactions. The lock ensures only one write happens at a time. The SQLite transaction ensures either the stock update AND the transaction record both commit, or neither does — no partial writes possible.

---

**Q: How do recommendations work?**

A: For each pair of products that appear as `pick` events in the same session ID, we increment a co-occurrence counter. When you query recommendations for product X, we return the products most frequently bought in the same session as X, sorted by count. No machine learning — it's a simple frequency table over the transaction log. This is deliberately lightweight per the project specification.
